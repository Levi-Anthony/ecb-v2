## 1. Focal referent and situated basis

Use the installed inquiry index `kappa = (R,B,G,F)`.

- **R — focal referent:** Capability Inspection / Verification Spine (CIVS): a reusable system by which a human or fresh worker can inspect what a capability is, where it physically exists, which objects/claims it depends on, what is mechanized versus semantic/human, how a result was derived, what proves each layer, what alternatives/dependencies remain, and how to reenter without inventing missing bridges.
- **B — boundary:** the inspection/verification system plus its first specimen, **Domain-Semantic Admission / D&I Boundary**. Included: Capability Inspection Record (CIR) contract, object connections, proof chain, physical-realization map, worked trace, installation ladder, ownership/dependency/reentry, portability and graceful-degradation inspection. Excluded from this plan: changing URG semantics; selecting a mathematical correspondence formalism; implementing autonomous semantic atomization/prior-art judgment; activating hosted circulation; refreshing connected-consumer schemas; claiming FR-3 or Quadrant performance uplift.
- **G — governing orientation:** make the capability personally inspectable, independently checkable at each standing level, and cold-agent reenterable; eliminate hidden bridges among prose, code, evidence, deployment, consumer availability and unresolved semantic judgments.
- **F — mapper/frame/access:** Principal/human inspection frame plus fresh-agent cold-reader frame. Evidence comes from exact GitHub objects, BRAIN receipts, Linear ownership/state, deployment records, and current native-source evidence. Access limitations remain explicit.

## 3. Planned Capability Inspection Record contract

Every CIR should contain:

1. Purpose and bounded claim.
2. Installation ladder:
   - specified;
   - implemented;
   - mechanically qualified;
   - integrated;
   - deployed;
   - exposed;
   - situated-use qualified;
   - operationally sustained.
3. Object connections: every consequential statement points to an actual code, contract, record, test, CI, deployment, issue, evidence, or Question Forward object; connection type is explicit.
4. Physical realization: repository → path/module → runtime/process → deployed service/revision → ingress → persistence → consumer surface.
5. Mechanized versus semantic/human judgments.
6. Worked execution trace through one real case.
7. Proof chain: premise → semantic judgment → structural gate → decision → test → CI → deployment → actual-use evidence.
8. Field-reconstitution role and all consequential upstream change classes.
9. Correspondence inspection: relation kind; source/target identity; basis; direction; cardinality where meaningful; semantic owner; evidence/standing/currentness; composition/inversion/partiality expectations; unresolved mathematical requirements.
10. Portability.
11. Graceful degradation.
12. Dependencies and owners.
13. Alternatives considered/rejected and why.
14. Known cold-reader bridges/wording defects.
15. Questions Forward, falsifiers and exact reentry.
16. Verification timestamp and supersession/currentness.

## 6. Alternatives rejected at planning stage
