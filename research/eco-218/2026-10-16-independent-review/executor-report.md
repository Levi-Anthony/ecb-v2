## Falsified baseline claims and repairs

1. **Session conservation was incomplete.** The independent evaluator executed baseline probes showing that a delayed refresh-token rejection sent Max-Age=0 after a sibling wrote a new pair; /api/personal could also rotate then drop the pair after an enrollment outage. Ordinary routes now perform remote getUser validation with a bearer-bound client, without refresh or cookie writes. Only explicit /oauth/refresh rotates. Successful rotation is returned immediately, before any work/enrollment call. No denied ordinary/refresh response erases cookies. Explicit logout is the only clearing action.
2. **Concurrent refresh was uncoordinated.** Both existing pages now use one shared session fetch script. Same-origin Web Locks serialize refresh, callback installation, email-code verification and logout across cooperative tabs in one profile. Under the lock, context is reread before refresh; a newly valid sibling session avoids a second rotation. Locked writers use raw fetch to avoid recursive-lock deadlock. No unsupported-browser unsafe lock fallback is introduced. The private page has a data-free expired-session bootstrap, so navigation itself can recover.
3. **A transient callback failure destroyed the retry path.** The original fragment was erased before session acknowledgment with no replay control. The fragment is still removed immediately for privacy; its pair is retained only in the page closure and an explicit Retry session recovery control reuses it. Success or definitive callback rejection drops the pending pair. No localStorage or token URL transfer is added. Closing/reloading that page before success still loses this in-memory retry; retain this limit.
4. **Outage UI encouraged false login recovery.** Provider/enrollment outages now retain retry status rather than falsely reporting no authentication. Initial login remains hidden until context is known. Known permanent refresh rejection gets a typed sign-in disposition without clearing cookies; a fresh context reread suppresses that disposition if a sibling already recovered. Unsupported locking has concrete current-Safari guidance. A confirmed email request hides its send form to reduce accidental duplicate sends.
5. **Existing OAuth methods needed session storage.** Pinned supabase-js/auth-js source inspection showed that SDK OAuth helpers call _useSession and may implicitly refresh; an Authorization header alone was insufficient for those helpers. The existing provider's same GET authorization-details, POST consent and DELETE grants APIs are called directly with the validated access bearer, publishable key and timeout. Existing native policy/grant RPCs and safeRedirect checks remain in place. This is an adapter within the same Supabase architecture, not a new authorization server. Logout uses the existing SDK admin.signOut(access, 'local'); failure is disclosed as native_revocation_pending while explicit browser signout clears local cookies.
