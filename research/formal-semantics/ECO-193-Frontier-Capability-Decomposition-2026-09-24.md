## 3. Defender versus Scout: alternatives tested

“Hard separation” here means explicit input/output and standing boundaries. It does not mean different agents, isolated models or duplicated source retrieval.

| Criterion | A. Separate callable contracts, composable routing | B. One Skill with a posture parameter | C. One capability with different presentation projections |
|---|---|---|---|
| Trigger | “What is earned?” and “Explore beyond this baseline” route separately | Can work if posture is explicit and never defaults ambiguously | A view change alone does not specify which work is requested |
| Standing/authority | Audit issues a bounded assessment; Scout issues candidates. Neither grants authority | Equivalent only if parameter switches genuinely different result contracts | Unsafe if a speculative record becomes an adjudicated claim by changing its view |
| Contamination | Candidate-to-assessment crossing must name evidence and method | A stale parameter or blended output can hide the crossing; type-specific contracts can repair it | Presentation labels cannot supply missing assessment |
| Cognitive load | User need name only the desired result; shared orientation avoids rereading everything | One entry may be convenient, but user must know the mode or router must infer it | Simple surface can conceal an unperformed change of job |
| Traceability | Proposal and assessed version remain linked and distinct | Adequate with explicit mode, source basis, claim and transition record | Adequate only after adding the same separate assessment event |
| Composition | Scout can be skipped; audit can consume outside proposals | Possible, provided internal routing is not a mandatory pipeline | Useful for rendering one result at different resolutions, not substituting between results |
| Independent usefulness | Audits of existing claims and speculative searches without immediate formalization both remain valid | Still requires both independently invocable behaviors | Shared purpose does not make their promised results identical |

**Decision:** A at the capability-contract level. Reuse the existing audit Skill and prototype Scout separately. A single technical entry point remains permissible if it enforces these distinct contracts; packaging is not the safety boundary. Reject C as a claim that these are merely views of the same output. A broad parent capability may compose both without erasing their differences.

**What would change this decision:** a controlled routing/output comparison showing that one explicitly parameterized entry performs equally well with lower burden, preserves proposal-to-assessment lineage, and never suppresses requested exploration or promotes its own speculation. Separate files alone are not evidence of improvement.

## 4. Standing invariants and routing

Apply these inherited safeguards within every affected invocation:

- Preserve the exact claim, referent, definitions, dependencies, purpose and standing. A rejected stronger hypothesis must not replace the user's actual claim.
- Keep observed source facts, analytical inferences, hypotheses, proposed decisions and authorized decisions distinguishable.
- Preserve proposals, rejections and reasons. A narrower surviving correspondence keeps its own scope; it does not erase the rejected version.
- Let Scout range beyond what Defender can endorse. Failure to be established is not a reason to forbid candidate generation.
- A mode switch changes the job, not the evidence. New standing requires an attributable assessment; governance promotion requires its independent route.
- A mathematical result, faithful mapping, useful next-step recommendation and authority to act are distinct.
- Use the notation contract below whenever consequential unfamiliar notation reaches the Principal. Source/effect contracts persist across Result, Handoff, Teach and Audit resolutions.

### First-use human-audit contract

At first meaningful introduction: **ORIENT → SYMBOLS → NAME/TOKEN → SAY FORMALLY → SAY NATURALLY when helpful → READ → WORKED EXAMPLE → SYSTEM APPLICATION.**

ORIENT identifies the construct, spoken convention, originating problem-family, ordinary job, present purpose and misleading inference to avoid. Exact spoken syntax and conceptual explanation are different outputs. Token names are supplied when unfamiliar; conversational speech is required when exact speech is awkward. On reuse, shorten established material without removing consequential meaning. Teach access should not depend on remembering an explanation from an unavailable earlier session.

This is **both** a standing operator-facing requirement and a shared helper. The standing rule ensures invocation; the helper owns the detailed projection. This return recommends that allocation but does not install a global rule or edit existing Skills.

### Routing rules

| Encountered need | Route | Exit |
|---|---|---|
| Material source, identity or standing missing | Orientation/source recovery then audit | A bounded evidence floor or exact blocked dependency |
| Earned baseline plus request for plausible leverage | Scout | Distinct candidates with plausible gain and discriminating lead; zero useful candidates is valid |
| Candidate lacks a hinge or branch consequence | Fulcrum profile | Decidable branches, method and consequence; OPEN if no discriminator yet |
| Selected question needs a formal correspondence | Translation | Mapping and explicit assumptions, consequence/countermodel, translated result, limits |
| Only notation or teaching access is missing | Notation helper | Existing statement made auditable; no reopened probe |
| Result is about to be used beyond its demonstrated envelope | Audit | Qualified scope or an explicit unsupported-use finding |
| Several consequential next inquiries compete | Next-probe composition | One recommendation and fallback, or none; authorization separate |

The familiar Defender–Scout–Fulcrum–Translation–Audit progression is one route, not a universal state machine. Translation embeds stress tests and may return directly to a semantic correction. Scout may use an already recovered baseline. A missing assumption can return to Fulcrum without replaying the entire sequence.

A sufficient handoff carries: exact claim/version, source basis, prior standing, active job, proposed change in standing, supporting result or unresolved discriminator, and next route. These are semantic obligations, not a mandated new schema or a transcript of internal reasoning.

- **Purpose/result class:** determine what a specified claim earns for a specified use.
- **Use when:** evidence, scope, provenance, currentness or authority could be conflated; includes evaluation of a completed Scout/Translation return.
- **Inputs:** exact proposition/referent/use; sources and editions; prior standing; assessment criteria and any claimed transition.

- **Outputs:** candidates stating correspondence, interesting feature, potential payoff, speculative standing, initial assumption/mismatch and candidate discriminator.
- **Side effects:** inquiry and read-only prior-art retrieval; no implementation, ontology change or promotion.
- **Standing/authority:** explicit exploratory remit. In this commission that remit comes from the prompt; future routing must recover it.
- **Semantic responsibilities:** allow productive overshoot, harvest real positive fit before attacking it, keep original semantics fixed, distinguish conjecture from established machinery.

### Discriminating inquiry design — Fulcrum profile

- **Purpose/result class:** convert a correspondence or consequential uncertainty into a condition whose different outcomes change what follows.
- **Use when:** resemblance is attractive but its load-bearing requirement, test or consequences remain unclear.
- **Inputs:** preserved proposition, purpose, candidate mapping, assumptions, competing possibilities and evidence access.
- **Outputs:** exact hinge; YES and NO consequences; mixed/underdetermined outcomes where real; fixture/method; stopping and reentry conditions; possible standing updates.
- **Side effects:** analysis/proposal only; defining a test does not run or authorize it.
- **Standing/authority:** inherit source standing; preserve a Principal intuition as attributed semantic input, not a proved fact.
- **Semantic responsibilities:** choose a genuine discriminator, preserve quantifiers/scope, avoid false dichotomies, distinguish exact correspondence from total identity.
- **Mechanical responsibilities:** validate that outcome branches, consequence, fixture and route exist and refer to the same target. Their discriminatory adequacy remains semantic.
- **Evidence/trace/failure:** record why alternatives would differ. If every branch leads to the same decision, revise the question or return no current discriminator.
- **Realizations:** profile/reference within QF; directly callable prompt projection; no separate Skill initially.
- **Composition:** uses Differentiate and Integrate when the candidate is fused; feeds Translation or a nonmathematical probe.

- **Non-trigger:** a simple missing date/source with a known retrieval path, or a settled exact test awaiting authorized execution.

- **Purpose/result class:** qualify one semantic-to-formal correspondence and return its practical meaning, including useful rejection.
- **Use when:** a precise semantic/operational claim may gain a derivation, constraint, falsifier or reusable mechanism from a formal representation.

### V5 — Corrected notation projection

This fixture projects ECO-192 §3.2 under both post-close corrections. It tests the presentation contract; it does not rerun or alter the mathematical result.

**ORIENT.** Reindexing, pronounced “ree-indexing,” retrieves an account through an explicit comparison of slots. Pullback notation in category theory commonly uses a superscript star, spoken “star”; here it marks this retrieval operation, not multiplication or permission. We use it now to show exactly which source record fills a matched destination slot. The general notation convention is illustrated in [Stacks §4.33](https://stacks.math.columbia.edu/tag/02XJ); the record interpretation is ECO-192's bounded construction.

**SYMBOLS**
`f: O_J → O_I`
`(f*X)(o) = X(f(o))`

**NAME / TOKEN.** O sub J is the set of destination slots; O sub I is the set of source slots. The colon declares a function's type; the arrow is read “to” in this expression. Lowercase o is a destination slot. X is the source account, assigning records to source slots. Parentheses denote application. f-star X is the account obtained by reindexing X along f.
