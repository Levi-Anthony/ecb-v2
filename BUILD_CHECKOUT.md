## BUILD 1–4 FRICTION HARVEST — FEED-FORWARD METHOD

The following is implementation-process evidence carried into BUILD 5. It constrains how Sense/Shape/
Move should be conducted where applicable; it does **not** itself add BUILD 5 ontology, schema, or
acceptance requirements.

### F1 — Qualify relevant prior art before authority-bearing invention

BUILD 1 demonstrated that independent derivation is valuable because it exposes the actual problem and
prevents historical imitation, but installation control still requires an explicit encounter with
settled prior art whose omission could change installation, protections, or interpretation of failure.

**Forward rule:** where BUILD 5 may reinvent, extend, or contradict inherited OB1/ECB history,
versioning, event, artifact, receipt, standing-transition, or currentness machinery, first derive enough
independently to expose the candidate problem, then compare against pinned relevant prior art before an
authority-bearing installation decision.

This is not a universal pre-action gate. Awareness remains a Metabolize feedback loop, not a reason to
preload all history.

### F2 — Any strengthened invariant over live state needs an explicit concurrency story

BUILD 2 showed that a correct steady-state invariant can still be violated during activation if a live
writer crosses the transition boundary under the old rules.

**Forward rule:** for every BUILD 5 candidate that adds or strengthens an invariant over existing
canonical records, Sense/Shape must ask:

> What can a concurrent writer observe or commit while this transition activates?

The answer may be "no special mechanism required," but it may not remain implicit.

### F3 — Preserve Layer A historical authority; project Layer B regression forward

BUILD 3 and BUILD 4 established a two-layer regression model:

- **Layer A:** frozen historical harnesses/receipts remain provenance of what their own Build Unit
  originally proved;
- **Layer B:** later builds create minimum current-state projections proving the enduring behavior still
  holds after lawful expansion.

**Forward rule:** do not rewrite or weaken frozen BUILD 0–4 acceptance authority to accommodate BUILD 5.
If BUILD 5 lawfully changes whole-schema cardinality or surface shape, preserve the historical harness
and create only the minimum new cross-build regression required to prove enduring behavior.

### F4 — Validate the validator before canonical contact

BUILD 3/4 friction clustered in harnesses and assertions rather than architecture: SQL/test wiring,
format/check failures, an incomplete inherited-constraint expectation, a vacuous always-pass assertion,
an over-specified constraint-name expectation, and a probe that accidentally registered its own
"unregistered" endpoint.

**Forward rule:** before any BUILD 5 mutation-bearing probe contacts canonical state, perform a
lightweight probe-integrity pass:

- format/type/static checks pass;
- fixture identities are checked for accidental reuse or self-fulfilling setup;
- no tautological or vacuous assertions survive;
- inherited-schema expectations are checked against the actual committed predecessor surface; and
- negative probes freeze the contractual behavior, not incidental database error ordering or constraint
  names unless that ownership is itself part of the contract.

This is validation of executable evidence, not an additional architecture stage.

### F5 — Select migration execution mechanics explicitly

BUILD 3 used the managed migration runner and inherited an outer transaction around a migration already
carrying its own transaction. BUILD 4 used byte-identical direct execution, gaining clear
artifact-to-execution provenance while leaving schema activation and migration-ledger insertion as two
separate commits. Both were accepted for their own builds; neither is precedent.

**Forward heuristic:** before BUILD 5 Move, state the required atomicity and provenance properties of
activation, including whether schema/data activation and migration-ledger recording must commit as one
indivisible transition. Then select the execution mechanism that actually provides those properties.

Do not inherit BUILD 3's runner or BUILD 4's direct application merely because it was used before.

### F6 — Canonical contact must buy information

Rollback probes, concurrency probes, independent reproduction, and cross-build regression are valuable
when they answer a live evidentiary question. Re-running a mutation-bearing harness against an unchanged
commit merely because a documentation seam occurred adds canonical contact without necessarily adding
information.

**Forward heuristic:** every canonical probe should name the uncertainty or falsifier it resolves. Do
not substitute ritual reruns for new evidence.

### F7 — Classify discrepancies before reopening architecture

BUILD 3/4 demonstrated that a failed test is not automatically a failed Shape.

At Metabolize, classify any discrepancy first as one or more of:

```text
SHAPE_OR_CONTRACT_DEFECT
IMPLEMENTATION_DEFECT
TEST_OR_PROBE_DEFECT
EXECUTION_OR_TOOLING_DEFECT
```

Only a discrepancy that actually reaches the Shape/contract layer, or exposes a recorded reopening
condition, justifies reopening architecture. This classification must not be used to excuse a real
architectural defect as "just tooling."

### Feed-forward boundary

The durable lessons are the rules above, not the accidents that produced them.

Do **not** canonize BUILD 4's constraint list, direct PostgreSQL execution, BUILD 3's independent digest
implementation count, specific fixture UUID patterns, or universal rerunning of every historical
harness. The observed weak surface across BUILD 1–4 is the translation from precise Shape into precise
executable proof; BUILD 5 should improve proof construction rather than add architecture ceremony.
